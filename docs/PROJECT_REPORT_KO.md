## 2. 출발점: 논문과 원본 코드

- **논문:** *Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki* (arXiv 2605.25480). 공식 코드: WeAgentAI/LLM-Wiki.
- **카파시의 LLM Wiki gist와의 차이:** 카파시 gist는 "LLM이 raw 문서를 읽고 마크다운 위키를 유지한다"는 아이디어 메모다. 이 논문은 그 아이디어를 검색 시스템으로 구현하고 평가했다.
  - **2단계 ingest:** Step 1에서 관련 기존 페이지를 고르고, Step 2에서 페이지를 새로 쓰거나 갱신한다.
  - **에이전트 검색:** 임베딩 대신 `wiki_search`/`wiki_read` 도구로 링크를 따라가며 추론한다 (Retrieval as Reasoning).
  - **Error Book:** lint에서 나온 오류 유형을 기록하고, 다음 ingest 프롬프트에 제약으로 주입한다. 2회 연속 깨끗하면 닫는다 (자기교정).
- **원본 코드를 그대로 쓸 수 없었던 이유 (계획 단계 감사 결과)**
  - **한국어 처리**
    - BM25 토크나이저가 `[a-z0-9]+`라 한글을 색인하지 못했다.
    - 프롬프트가 "English page names"를 강제했다.
    - 섹션 제목을 정확한 영어 문자열로 검사해서, 한국어 제목을 쓰면 lint와 수리가 무한 반복됐다.
    - 파일명이 255바이트를 넘으면 실행이 중단됐고, NFC 정규화도 없었다.
  - **Error Book이 논문 설명과 다름**
    - 기본 모드(배치)에서는 제약이 프롬프트에 주입되지 않았다.
    - 일부 유형은 영원히 closed가 되지 않았다.
    - 깨끗한 lint에서 pass_count가 오르지 않았다.
  - **입력 형식:** 내 raw는 정형 테이블인데, 파이프라인은 "문서 1개 = md 1개"를 기대했다.
  - **실행 경로:** 벤치마크 데이터셋 3종이 하드코딩돼 있었고 경로 버그가 있었다. OpenAI에 vLLM 전용 파라미터(`chat_template_kwargs`)를 보냈다.

## 3. 계획

### 3-1. 계획을 세운 방법

1. 논문과 코드 구조를 먼저 파악했다 (Q&A 3회).
2. 계획 모드에서 감사 에이전트 2개를 병렬로 돌렸다.
   - 하나는 "Error Book과 증분 ingest 동작 추적"을 맡았다.
   - 다른 하나는 "한국어 대응 감사"를 맡았고, 프롬프트 24곳과 매칭 버그를 찾았다.
3. gpt-6-luna API의 파라미터 호환성을 웹에서 조사했다. `max_completion_tokens`, `reasoning_effort`, 그리고 도구 호출은 effort가 `none`일 때만 지원된다는 점을 확인했다.
4. 선택지를 질문으로 확정한 뒤 단계별 계획(0~8단계)을 세우고 승인받았다.

## 4. 세팅 (다시 돌리는 방법)

### 4-1. 환경

| 구성 | 내용 |
|---|---|
| OS | macOS (Darwin 25) |
| Python | 3.10 이상. `make setup`이 `.venv`를 만들고 패키지를 editable로 설치한다 |
| Node / npm | Node 22.12 (nvm), npm 10.9.9 (Quartz 5는 npm 10.9.2 이상 필요해서 올림) |
| Quartz | `.quartz/`에 자동 설치. v5 브랜치 커밋 `97a2d05` 고정 (§9) |
| GitHub | `gh` CLI로 fork, push, Pages 활성화 |
| API 키 | `.env`의 `OPENAI_API_KEY` (git 제외) |

### 4-2. `.env` 주요 설정

```ini
OPENAI_API_KEY=...                 # git에 올리지 않음
OPENAI_BASE_URL=https://api.openai.com/v1
LLM_PREMIUM_MODEL=gpt-6-luna       # Step 2 페이지 작성, 페이지를 만드는 수리
LLM_FAST_MODEL=gpt-6-luna          # Step 1 페이지 선택, lint 수리, 답변
LLM_REASONING_EFFORT=low           # 텍스트 호출. 도구 호출은 항상 none
WIKI_LANG=ko
WIKI_CORPUS=assembly_spc
WIKI_DUMP_PROMPTS=0                # 1이면 Step 1/2 프롬프트를 파일로 저장
```

### 4-3. 명령 흐름

```bash
make setup                 # .venv + 패키지 설치 + .env 복사
make prepare               # 예제 문서 154개, purpose, page_types 배치 (PRESET=small이면 27개)
make build                 # 전체 구축 (~80분) → "built" 스냅샷 저장
make ask Q="질문"           # 에이전트 질의 (search → read → 링크 추적 trace 출력)
make demo-errorbook        # 결함 3개 심기 → lint 기록 → 주입될 제약 표시
make demo-add              # 새 문서 5개 추가 (~4분, 제약 주입·수리)
.venv/bin/llm-wiki lint    # 검증 → 2회 연속 깨끗하면 closed
make demo-reset            # "built" 상태로 복원
make site PORT=8090        # 로컬 Quartz (8080은 다른 Java 프로세스가 사용 중)
make deploy-pages          # 정적 사이트를 gh-pages로 배포
```

### 4-4. 데이터 변환 (raw → 문서)

## 6. 왜 v1, v2 두 번 구축했나

결론부터 말하면 **v1 구축 중 원본 코드의 "출처 손실" 버그가 드러났기 때문**이다. 이 버그 때문에 정상 사실이 대량으로 삭제됐고, 버그를 고친 뒤 처음부터 다시 구축한 것이 v2다.

1. **small 구축 (27개):** 먼저 작게 돌려 문제 두 가지를 찾아 고쳤다.
   - **근거 검증(grounding):** digest 요약 3,000자만 근거로 써서 정상 사실 82개를 지웠다. 원문 기사를 최대 20,000자까지 근거로 쓰도록 고쳤고, 사실의 절반 이상이 "근거 없음"으로 나오면 삭제하지 않고 건너뛰게 했다.
   - **깨진 링크 연쇄:** 수리로 새로 만든 페이지가 또 없는 페이지로 링크를 걸었다. 실제 존재하는 페이지만 링크하도록 고쳤다.
2. **v1 전체 구축 (154개):** 구축 자체는 성공했다 (168페이지). 하지만 근거 검증이 **사실 250개**를 지웠다.
   - **원인 (출처 손실):** 뒤 배치가 기존 페이지를 갱신할 때 `## Related Sources`(출처 digest 링크)를 새로 쓰면서 기존 출처를 잃었다.
   - 그러면 근거 검증이 그 페이지의 사실을 **엉뚱한(최근) 문서와만 대조**하게 되고, 원래 출처에 있던 정상 사실을 "근거 없음"으로 판단해 지웠다.
   - 같은 맥락에서, LLM이 digest 링크 번호를 잘못 쓰거나 없는 digest를 지어내는 문제도 확인했다.
3. **수정:**
   - 페이지를 덮어쓸 때 기존 출처를 합친다 (`_merge_related_sources`).
   - 배치 프롬프트를 "기존 출처 유지"로 바꿨다.
   - digest 링크를 접두어·ID·제목으로 대조해 바로잡고, 못 찾으면 제거한다 (`_resolve_digest_links`).
4. **v2 재구축:** 이미 쓰인 페이지에는 출처가 빠져 있어 사후 수리가 어려웠다. 그래서 처음부터 다시 구축했다.
   - 비용은 약 $0.7로 작고, 시간만 약 80분 걸린다.
   - 중간에 중단을 요청받았는데, ingest 캐시(`.wiki-cache-bench-assembly_spc.json`) 덕분에 처리한 60개를 건너뛰고 이어서 끝냈다.

| | v1 | v2 |
|---|---|---|
| 지식 페이지 | 168 | 179 |
| 근거 검증으로 삭제된 사실 | **250** | **32** |
| 정당·위원회·사건·본회의 페이지 | 3 / 1 / 18 / 10 | 4 / 3 / 21 / 14 |
| 최종 lint | — | 0건 |
| 같은 38문항 평가 | 38/38 (char-F1 1.000) | 38/38 (char-F1 0.975 / 0.923) |
| 구축 시간 | 78분 | 79분 (26분 + 재개 53분) |
| 보관 위치 | `wiki_output/assembly_spc_v1`, 스냅샷 `full-v1` | `wiki_output/assembly_spc`, 스냅샷 `built` |

- **평가 점수에 대한 해석:** 두 버전 모두 정답을 맞혔고, v2의 char-F1이 조금 낮은 것은 답을 더 길게 쓴 영향이다.
- **v2를 쓰는 이유:** 정답률이 같아도 v2를 시연 기준본으로 삼았다. v1은 사실 250개가 빠진 위키라서, 질문 범위가 넓어지면 답을 못 하는 경우가 생긴다.
- **v1을 보관하는 이유:** 버그가 있을 때와 고친 뒤를 비교해 보여주기 위해서다.

## 7. 구축하며 고친 원본 코드 문제 (요약)

자세한 내용은 [CHANGES_KO.md](CHANGES_KO.md)에 있다.

- **Error Book 논문 정합**
  - 배치 모드에도 제약을 주입한다.
  - 깨끗한 lint도 기록해 pass_count가 오른다.
  - LLM 수리 대상 유형도 2회 연속 미탐지면 closed가 된다.
  - 다시 탐지되면 연속 횟수를 초기화한다.
  - 깨진 링크 샘플을 중복 없이 센다.
  - 막힌 덮어쓰기를 `unseen_page_overwrite`로 기록한다.
- **수리 품질:** 근거 검증, 깨진 링크 연쇄, 출처 손실, digest 링크 오류 (§6).
- **한국어**
  - 프롬프트에 언어 지시와 한국어 예시를 넣었다.
  - 한글 bigram BM25를 적용하고, 조사를 떼고 매칭한다.
  - 파일명에 NFC를 적용하고 200바이트로 제한한다.
  - 한국어로 나온 섹션 제목을 영어로 정규화한다.
  - 짧은 이름의 부분 일치를 막는다 (조국 ≠ 조국혁신당).
- **실행 경로:** 데이터셋 하드코딩과 경로 불일치를 고쳤다. reasoning 모델 파라미터를 지원하고, 4xx는 즉시 실패시킨다.
- **증분 추가:** `add`가 배치 모드와 light finalize로 동작한다. 새 사실이 있는 기존 페이지도 갱신하고, 작업 내용을 `log.md`에 기록한다.
- **테스트:** API 호출 없는 오프라인 테스트 29개, 모두 통과.

## 10. API 비용 (OpenAI gpt-6-luna)

### 10-1. 실측이 아닌 추정인 이유

- 이 프로젝트의 API 키는 project 키라서 사용량 API(`/v1/organization/costs`)를 부르면 `api.usage.read` 권한이 없다는 403이 난다.
- 구축할 때 `--log-llm`(호출별 토큰 로그)을 켜지 않아서, 로그에도 토큰 수가 없다.
- **정확한 금액**은 OpenAI 대시보드 Usage 페이지(platform.openai.com/usage)에서 2026-10-23~24, 해당 프로젝트로 확인할 수 있다.
- 다음부터는 `llm-wiki <명령> --log-llm`으로 실행하면 호출마다 토큰 수가 로그에 남는다.

### 10-2. 추정 근거 (실측값)

- **단가:** gpt-6-luna는 입력 $0.10, 출력 $0.50 (100만 토큰당). 계획 단계에서 웹으로 확인했다.
- **배치 프롬프트 크기:** 리허설 때 저장한 프롬프트 6개를 o200k 토크나이저로 셌다. 위키가 다 찬 상태(179페이지) 기준이다.
  - Step 1(선택): 19,000~21,000 토큰
  - Step 2(작성): 18,000~26,000 토큰
- **문서와 위키 크기:**
  - 원문 문서 154개는 18만 토큰이다 (평균 1,170).
  - 최종 지식 페이지 179개는 13.6만 토큰, digest는 11.2만 토큰이다.
- **호출 구성:**
  - 전체 구축 1회 = 77배치 × (Step 1 + Step 2).
  - 여기에 근거 검증이 5회 × 30페이지, 모순 검사가 5회 × 10쌍 붙고, 구조 수리 몇 건이 더해진다.
  - 평가 1문항은 도구 호출 평균 3.1~3.9회와 답변 1회다.
- **가정:**
  - 구축 중에는 위키가 커지면서 프롬프트도 커지므로, 평균을 최종 크기의 약 70%(배치당 입력 약 3만 토큰)로 잡았다.
  - 배치당 출력은 약 7천 토큰으로 잡았다 (페이지 5~7개와 추론 토큰).
